看起来只是"状态未同步"，却让 drain 永远卡住的 PDB

一个控制器算不出来的 PodDisruptionBudget 如何让 kubectl drain 无限重试，以及如何在 cordon 之前发现它。

现象

你 drain 一个节点，有一个 Pod 怎么也走不掉。取决于这个 PDB 之前是否同步成功过，kubectl drain 要么一直重复 Cannot evict pod as it would violate the pod's disruption budget，要么打印一行 evicting pod ... 之后就再无输出。可这个 PDB 看上去没问题：maxUnavailable: 1，选中的 Pod 全部 Ready，没有不健康的副本，也没有重叠的 PDB，kubectl get pdb 却显示 ALLOWED DISRUPTIONS 0。

原因

要把 maxUnavailable（或百分比形式的 minAvailable）换算成具体数字，disruption 控制器需要知道期望副本数。它沿着每个被选中 Pod 的 controller ownerReference 找到属主，再读属主的 scale 子资源。Deployment、ReplicaSet、StatefulSet 都有，但很多 Operator 的 CRD 没有。

查不到时，控制器走兜底逻辑：把 disruptionsAllowed 置 0，并写入一个 condition：

status:
  disruptionsAllowed: 0
  conditions:
  - type: DisruptionAllowed
    status: "False"
    reason: SyncFailed
    message: widgets.example.com does not implement the scale subresource

此后 Eviction API 对每次驱逐都返回 429，而 kubectl drain 把 429 当作"稍后重试"，于是永远重试下去。托管节点组升级只能等到自己的超时。

陷阱：它看起来只是"过期"

兜底逻辑不会更新 status.observedGeneration。一个从未同步成功的 PDB，observedGeneration 会一直小于 metadata.generation，和刚修改完、控制器还没追上的几秒钟里一模一样。把它理解成"状态还没处理，等一下就好"的工具都会预测为短暂等待。drainready 在本周之前也是这样判断的。

这也解释了 drain 为什么会"沉默"。对服务端认为尚未处理的 PDB，Eviction API 返回带 Retry-After 头的 429，client-go 会在 kubectl 看到错误之前自行重试。在我们的 kind 测试里，kubectl drain --dry-run=server --timeout=10s 打印出 evicting pod ops/widget-0 后，20 秒内再无任何输出，直到测试把它杀掉。

手动检查

kubectl get pdb -A -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}{"\t"}{.status.conditions[?(@.reason=="SyncFailed")].message}{"\n"}{end}' | awk -F'\t' '$2!=""'

输出的每一行，都是一个在修好之前会挡住其 Pod 所有自愿驱逐的 PDB。

修复办法

  • 改用整数 minAvailable：控制器直接数被选中的 Pod，不需要查 scale。
  • 给 CRD 加上 /scale 子资源（CRD spec 里的 subresources.scale），让控制器能读到副本数。
  • 收窄 selector，只覆盖带 scale 子资源的控制器所管理的 Pod。

在 cordon 之前

drainready 现在会先检查 DisruptionAllowed condition，再看 observedGeneration（已在 main 分支，随下个版本发布），把这类 Pod 报为 BLOCKED，引用控制器的原始报错，并给出修复建议：

$ drainready ip-10-0-3-17
BLOCKED  ip-10-0-3-17   7 pods: 4 ok, 0 wait, 0 need flag, 1 blocked, 2 skipped
   BLOCKED  ops/widget-0  PDB ops/widget cannot be computed by the disruption controller (SyncFailed: ...), so it allows 0 disruptions
                          fix: maxUnavailable and percentage minAvailable need every selected pod to belong to a controller with a scale subresource ...

CI 在真实的 kind 集群里用一个属主为 ConfigMap 的 Pod 复现这个场景，并用 kubectl drain --dry-run=server 交叉验证。加上 --markdown 可以生成直接贴进变更单的报告。
